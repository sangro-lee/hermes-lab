# 아키텍처 설명

```text
사용자 / 연구자
      │ 승인·방향 설정
      ▼
Hermes (오케스트레이터)
  ├── 연구 상태와 미해결 질문 읽기
  ├── 다음 작업 계획 제안
  ├── 작업을 적절한 도구/에이전트에 위임
  ├── 결과 요약 및 연구 기록 갱신 제안
  └── 승인 정책 확인
       ├── 문헌·문서 검색 도구 (MCP 등)
       ├── Claude Code: 코드 검토/구현 보조
       ├── Codex: 코드 수정/테스트 보조
       └── researchctl: 허용된 HPC 작업 인터페이스
                    │
                    ▼
             Slurm / Linux GPU 노드
                    │
                    ▼
          실험 결과·로그·체크포인트
                    │
                    ▼
       분석 → 결과 검토 → Research State 갱신
```

## 설계 원칙
1. 오케스트레이터와 작업자를 분리한다. Hermes가 연구 진행을 조율하고, 코딩 에이전트는 명확한 작업 단위를 수행한다.
2. 연구 기록은 대화 기록만으로 관리하지 않는다. `research/`의 상태 파일과 `experiments/`의 실험 명세를 프로젝트 저장소에 둔다.
3. GPU 실행은 통제된 인터페이스를 통한다. 처음부터 에이전트에게 임의의 `sbatch`, `scancel`, `sudo` 권한을 주지 않는다.
4. 결과와 코드 버전을 연결한다. 각 실험에 Git commit, 데이터 버전, 설정, seed, 로그 경로를 남긴다.
5. 성공 여부는 사전에 정의한 metric과 baseline으로 판단한다.

| 요소 | 역할 | 도입 시점 |
|---|---|---|
| Hermes | 장기 연구 흐름 조율 | 초기 |
| Claude Code / Codex | 코드 분석·수정·테스트 | 초기 |
| MCP | 에이전트가 도구/데이터를 표준 방식으로 호출 | 필요할 때 |
| Slurm | HPC 자원 예약과 작업 실행 | GPU 실험 단계 |
| JSON Schema | 실험 명세 형식 검증 | 초기 |
| Git | 코드와 문서 변경 이력 | 초기 |
| DVC | 대용량 데이터·산출물 버전 추적 | 복잡해질 때 |
| Cron / systemd timer | 정해진 시각에 점검·요약 실행 | 안정화 이후 |
| OpenTelemetry | 도구 호출·실행 단계의 trace/metric/log | 구성 요소가 늘어난 뒤 |
| Prefect / Temporal | 실패 복구·재시도·장기 워크플로 | 복잡해질 때 |
| A2A | 에이전트 간 상호작용 | 다중 에이전트 확장 시 |

모든 기술을 첫날부터 설치할 필요는 없습니다. 초기에는 Hermes + 코딩 에이전트 + 명시적인 연구 상태 + Git + 제한된 Slurm 실행 흐름부터 검증합니다.
